# DNS Behavior Review

## Purpose

This document records the workstation DNS behavior during VPN-active testing.

Raw DNS outputs are stored locally under private/raw/ and must not be published.

## VPN Active Test

During the VPN-active DNS test, the ProtonVPN WireGuard interface was detected.

| Item | Result |
|---|---|
| VPN interface | vpn0 |
| Public route decision | via vpn0 |
| VPN routing table | 51820 |
| systemd-resolved | disabled / inactive |
| resolv.conf generator | resolvconf |
| Quad9 direct detection | detected |
| DNS validation status | partially validated |

## Routing Result

The route decision for a public IPv4 destination selected the ProtonVPN WireGuard interface.

This confirms that public traffic was routed through the VPN policy routing table during the test.

## DNS Result

The active /etc/resolv.conf file was generated by resolvconf and contained nameserver entries.

A direct Quad9 check succeeded.

Result:

Quad9 DNS detected directly in /etc/resolv.conf

## Difference From Earlier Baseline

Earlier DNS checks did not detect Quad9 directly in /etc/resolv.conf.

During this VPN-active test, Quad9 was detected directly.

This suggests that DNS behavior changes depending on VPN state or resolver management state.

## Current Assessment

With ProtonVPN active:

- VPN interface was detected
- public route decision used vpn0
- policy routing table 51820 was used
- Quad9 was detected directly in /etc/resolv.conf

This is a good result for the VPN-active state.

However, this does not yet fully prove DNS leak protection.

## Remaining DNS Tests

The following checks are still required:

1. DNS behavior with VPN disabled.
2. DNS behavior immediately after VPN activation.
3. DNS behavior immediately after VPN disconnection.
4. DNS leak test using an external trusted test site.
5. Resolver comparison between VPN-on and VPN-off states.
6. Decision on whether Quad9 should be enforced outside VPN.

## Sensitive Information Excluded

- full raw NetworkManager DNS output

| Item | Result |
|---|---|
| VPN interface | not detected |
| Public route decision | via Wi-Fi interface |
| systemd-resolved | disabled / inactive |
| resolv.conf generator | resolvconf |
| Quad9 direct detection | not detected |
| DNS validation status | VPN-off behavior documented |

## VPN On vs VPN Off Comparison

| State | Public Route | Quad9 Direct Detection | Assessment |
|---|---|---|---|
| VPN active | via vpn0 / table 51820 | detected | Preferred state |
| VPN inactive | via Wi-Fi interface | not detected | Requires review |

## Current DNS Assessment

The workstation behaves differently depending on VPN state.

When ProtonVPN is active, public traffic is routed through the VPN interface and Quad9 is detected directly in /etc/resolv.conf.

When ProtonVPN is inactive, public traffic uses the regular Wi-Fi route and Quad9 is not detected directly in /etc/resolv.conf.

This means DNS behavior is acceptable in the VPN-active state but not fully controlled in the VPN-off state.

## Follow-Up Decision

A future hardening step should evaluate whether the workstation should enforce one of the following models:

1. VPN-required mode with firewall-based kill switch.
2. ProtonVPN/native kill switch mode.
3. Quad9 enforced even when VPN is off.
4. Normal VPN-off fallback accepted as a documented tradeoff.

The current preferred direction is to evaluate a VPN kill switch after the inventory phase is complete.
