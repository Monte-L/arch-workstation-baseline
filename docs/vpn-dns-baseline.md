## Routing Behavior

The main routing table still shows the Wi-Fi interface as the default route.

However, policy routing rules are present, and the route decision for a public IPv4 address selected the VPN interface.

Observed sanitized route decision:

- dev protonch
- table 51820

This indicates that the VPN is active and that public traffic is being routed through the ProtonVPN WireGuard interface using policy routing.

## DNS State

DNS is managed by NetworkManager through /etc/resolv.conf.

A direct check against /etc/resolv.conf did not detect Quad9 public resolver addresses.

| Item | Status |
|---|---|
| DNS manager | NetworkManager |

| /etc/resolv.conf | Generated by NetworkManager |
| Quad9 direct detection | Not detected directly |
| DNS validation status | Requires further testing |

## Current Assessment

VPN routing appears to be working correctly during the active VPN test.

The workstation uses ProtonVPN through a WireGuard interface named protonch.

Although the main routing table shows Wi-Fi as the default route, policy routing sends public IPv4 traffic through the VPN interface.

DNS behavior still requires additional validation because Quad9 was not detected directly in /etc/resolv.conf.

## Required Follow-Up Tests

1. Verify external IP before and after VPN activation.
2. Verify DNS resolver behavior while VPN is active.
3. Check for DNS leaks.
4. Confirm whether DNS is handled by ProtonVPN, Quad9, or NetworkManager.
5. Decide whether Quad9 should be enforced outside the VPN.
6. Document expected behavior for VPN-on and VPN-off states.

## Sensitive Information Excluded

The following information must not be published:

- WireGuard private keys
- WireGuard peer public keys
- VPN endpoints
- public IP addresses
- DNS resolver IPs, unless intentionally documented
- local gateway IP address
- full routing table
- full WireGuard configuration
- raw VPN status output
